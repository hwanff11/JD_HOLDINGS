# JDSS 3.1 TWIN-H40-S3 최종 사양

이 문서는 `JDSS-3.1.0-TWIN-H40-S3`의 전략·회계·주문 계약이다. 수치 설정은 루트 `strategy.yaml`, 구현은 `src/jd_holdings`, 현재 배포 상태는 `CURRENT_WORK.md`가 기준이다.

## 1. 범위와 안전 상태

- 초기 JDSS 전략 배정금: `$20,000`
- 거래 대상: TQQQ, SOXL
- 기초자산: TQQQ→QQQ, SOXL→SOXX
- 유휴자금: SGOV, 최소 현금 버퍼 `$250`
- 운영 단계: `dry_run` 전용
- `portfolio.live_enabled`는 반드시 `false`여야 한다.
- V3 설정으로 프로세스를 `live`에서 시작하거나 코어 매수를 live 주문으로 실행하면 코드가 거부한다.

## 2. 월간 쌍발 코어

각 기초자산은 독립적으로 다음 규칙을 적용한다.

1. 완료된 마지막 월말 거래일을 확정한다.
2. 해당 월말까지의 월별 마지막 종가로 6개월 단순이동평균을 계산한다.
3. 월말 종가가 6개월 평균보다 엄격히 높으면 대응 레버리지 ETF 코어를 ON, 같거나 낮으면 OFF로 둔다.
4. OFF→ON으로 처음 전환된 달의 목표는 **JDSS 관리 평가액(managed equity)** 의 10%다.
5. 다음 월말에도 ON이 유지되면 목표를 15%로 높이고 이후 ON 동안 15%를 유지한다.
6. OFF가 되면 목표는 0%로 돌아가고, 다음 ON은 다시 10%부터 시작한다.
7. 목표수량은 매수 수수료를 포함해 정수주 내림한다.
8. 목표와 현재 코어 차이가 JDSS 관리 평가액의 0.5% 미만이면 거래하지 않는다.
9. 신호는 완료 월말 뒤 첫 허용 세션에서 처리한다.

`managed equity`는 JDSS가 관리하는 현금 + JDSS 코어·부스터 + JDSS 관리 SGOV의 시장가치만 포함한다. 같은 Toss 계좌에 별도 개인 현금, 개인 TQQQ·SOXL, 개인 SGOV가 있어도 코어 목표비중 계산에 포함하지 않는다.

코어 매수는 Telegram 2단계 승인이 필요하다. 추세 OFF 또는 목표 초과로 발생한 코어 매도는 위험축소이므로 자동 제출한다.

## 3. JDSS H40-S3 부스터

JDSS 과매도·반등 규칙의 **종목별 자금 상한(cap)** 은 `$8,000`, 즉 초기 총자금의 40%다. 다만 현재 S3는 누적비중을 40%→70%→90%까지만 사용하므로 재매수가 비활성화된 정상 한 사이클의 실제 최대 신규투입액은 `$7,200`, 즉 초기 총자금의 36%다. `H40`은 자금 상한을 뜻하며 매 사이클마다 반드시 40%를 전부 투입한다는 뜻이 아니다.

- 진입 최소점수 55, 반등점수 최소 5, RED 국면 신규·추가매수 차단
- 3단계 비중: 40% / 30% / 20%, 누적 40% / 70% / 90%
- 추가매수: 최초 체결가 대비 -2% / -5%
- SOXL 섹터 가드: SOXX 또는 SMH가 EMA60 아래면 1·3차 차단
- 익절: 평단 +4%에서 약 30%, +10%에서 잔량
- TP1 이후 기간 기준 잔여청산 비활성화
- 자동손절과 재매수 비활성화
- 모든 부스터 매수는 기존 2단계 Telegram 승인 필수

4차 추가매수는 제거한다. 연구에서 4차를 추가하면 CAGR은 18.81%에서 18.95%로 0.14%p 늘었지만 MDD는 -26.04%에서 -26.57%로 악화되고 Sortino도 1.197에서 1.195로 소폭 낮아졌다.

## 4. 통합 계좌와 관리원장

- **managed cash**는 초기 JDSS 배정금 `$20,000`에서 시작해 JDSS 주문원장의 실제 누적 체결만 반영한다. 매수는 체결대금+설정 수수료를 차감하고 매도는 체결대금-설정 수수료를 더한다.
- 아직 체결되지 않은 BUY 주문의 잔여 지정가 금액과 예상 매수수수료는 예약현금으로 차감한다.
- 실제 브로커 USD 주문가능금액이 managed cash보다 작으면 더 작은 실제 브로커 금액을 실행 상한으로 사용한다.
- 실제 브로커에 개인 현금이 더 있어도 JDSS는 managed cash를 초과한 BUY 주문을 중앙 주문 게이트에서 거부한다.
- `positions`는 JDSS 부스터 수량·평단·원가·TP 상태만 기록한다.
- `core_positions`는 코어 수량·평단·원가·추세·목표비중·신호일을 기록한다.
- `idle_cash_state`는 JDSS가 직접 매수한 SGOV 관리수량만 기록한다.
- 브로커 TQQQ·SOXL 수량의 기대값은 `부스터 수량 + 코어 수량`이다.
- 브로커가 같은 티커를 합산해 보여도 부스터 체결 반영에는 브로커 합산 평단·합산 수량을 사용하지 않고 해당 부스터 주문의 체결수량·체결가와 기존 부스터 원장만 사용한다.
- TP 주문수량 검증은 부스터 수량만 대상으로 한다.
- TP 부분체결 후 취소·재주문이 발생해도 이전 부분체결을 포함한 누적 TP 체결수량을 유지하고 포지션에는 신규 체결 delta만 반영한다.
- 코어와 부스터 체결은 각 원장에만 반영하며 같은 슬리브의 누적 체결을 두 번 적용하지 않는다.
- DB에 열린 주문이 있는데 broker order id가 없거나, 수량·미체결 주문·SGOV 관리원장이 브로커와 다르면 신규매수를 중단하고 SAFE_MODE 이벤트를 기록한다.

## 5. SGOV 자금관리

SGOV는 **JDSS 관리 유휴자금만** 운용한다. 목표는 `managed cash + JDSS 관리 SGOV 시장가치 - $250`이며 0 미만이면 0으로 둔다. 따라서 닫힌 사이클의 실현손익과 설정 수수료가 다음 유휴자금 운용에도 이어지고, 개인 현금이나 개인 SGOV는 목표금액에 편입되지 않는다.

- `$100` 이상 차이만 조정한다.
- 매수는 최우선 매도호가 +`$0.01`, 매도는 최우선 매수호가 -`$0.01`의 시장가성 지정가를 사용한다.
- 60초 미체결 주문은 취소한 뒤 다음 점검에서 재가격한다.
- 전략 매수 전에 필요한 JDSS 관리 SGOV만 먼저 현금화하고 체결·JDSS 관리 달러·실제 브로커 주문가능금액을 모두 확인한다.
- 기존 개인 SGOV는 관리원장에 자동 편입하거나 자동 매도하지 않는다.

## 6. 신호·주문·재시작 안전장치

- 일봉과 월봉은 모두 완료봉만 사용한다.
- 매수 허용 세션은 pre-market과 after-hours이며 regular 세션은 비활성화 상태다.
- 신호가격 대비 추격 상한 5%, 지정가 버퍼 0.5%를 적용한다.
- 검토 토큰 TTL 480분, 최종 실행 토큰 TTL 60초다.
- 가격·수량·세션이 최종 승인 뒤 바뀌면 기존 토큰을 폐기하고 재승인을 요구한다.
- 모든 주문은 결정적 `client_order_id`로 예약한 뒤 브로커에 제출한다.
- dry-run 재시작 시 보유량은 SQLite의 코어·부스터·SGOV 관리원장에서, 현금은 전체 JDSS 누적 체결원장에서 복원한다.
- 체결 0인 확인 가능한 DRY 미체결 주문은 동일 broker id로 복원하고 주문번호 sequence도 이어간다.
- `UNKNOWN` 주문과 재시작 시점의 `PARTIAL_FILLED` 주문은 메모리 브로커 상태를 추정해 정상으로 만들지 않는다. 주문번호 sequence는 소비하되 주문 자체는 복원하지 않고 Reconciliation이 SAFE_MODE로 전환하도록 한다.
- dry-run 프로세스 안에서 누적 부분체결을 갱신할 때는 이전 누적값과의 delta만 잔고·현금에 적용한다.

## 7. 백테스트 계약과 채택 근거

통합 백테스트는 코어와 부스터가 현금을 공유하는 단일 계좌로 계산한다.

- 월말 완료봉 신호, 다음 거래일 시가 체결
- 매수·매도 수수료 각 0.1%, 기본 슬리피지 0.1%
- 코어 10→15%, 부스터 자금 상한 40%, 실제 3단계 누적투입 최대 90% of cap
- 현금 버퍼를 제외한 잔여 현금에 SGOV 일수익률 반영
- 잔여 포지션은 매도 수수료를 반영한 청산가치로 평가

동일 조건 장기 연구에서 기존 V3.0과 최종 후보는 다음과 같았다.

| 지표 | V3.0 main | V3.1 채택 후보 |
|---|---:|---:|
| Total Return | +678.07% | +1372.96% |
| CAGR | 14.05% | 18.81% |
| MDD | -28.29% | -26.04% |
| Sharpe | 0.835 | 0.940 |
| Sortino | 1.004 | 1.197 |

수익률과 위험조정 성과가 동시에 개선되어 V3.1 후보를 채택했다. managed cash/equity와 재시작 안전장치는 실행·회계 계층의 보강이며 위 전략 수식과 production 백테스트 엔진은 변경하지 않는다.

## 8. 승격과 배포 게이트

`main` 병합 전 Ruff, 전체 pytest, 설정 검증, dry-run 통합 테스트와 문서 계약 테스트가 통과해야 한다. Oracle 배포 시에도 live 잠금은 유지한다.

`config_version`이 바뀌는 배포는 기존 부스터 사이클이나 미완료 주문이 있으면 배포 스크립트가 중단하고 기존 서비스를 복구한다. 배포 직후 managed cash·managed equity와 Reconciliation 결과를 확인한다.

```dotenv
JDSS_TRADING_MODE=dry_run
JDSS_LIVE_CONFIRMATION=
```

live 승격은 별도 전략 검증·운영자 승인·코드 변경 없이는 불가능하다.
