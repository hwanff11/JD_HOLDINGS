# JDSS V3.1.1 TWIN-H40-S3 최종 사양

이 문서는 `JDSS-3.1.1-TWIN-H40-S3`의 공식 전략·자금·주문 계약이다. 숫자 설정은 저장소 루트 `strategy.yaml`, 구현은 `src/jd_holdings/`, 현재 배포 상태는 `CURRENT_WORK.md`가 기준이다.

## 1. 전략 범위와 고정 자금 계약

- 거래 대상: **TQQQ, SOXL**
- 기초자산: TQQQ→QQQ, SOXL→SOXX
- JDSS 고정 전략원금: **$50,000**
- 외부 추가입금: JDSS 자금에 편입하지 않음
- JDSS 실현수익: **다음 매매 사이징에 재투자하지 않음**
- 손실 발생 시: 개인 현금으로 자동 보충하지 않음
- SGOV: **사용하지 않음**. 미투입 JDSS 원금은 USD 현금으로 유지
- 개인 QQQ/QQQM/현금: 같은 Toss 계좌에 있어도 JDSS 원장에서 제외
- 개인 TQQQ/SOXL: 같은 Toss 계좌에 혼합 보유 금지
- 운영 모드: `dry_run` 전용, `portfolio.live_enabled=false`

`$50,000 고정`은 브로커 계좌 전체 잔액을 $50,000으로 맞춘다는 뜻이 아니다. JDSS가 사용할 수 있는 원금 한도를 $50,000으로 고정한다는 뜻이다. JDSS가 이익을 내어 실제 Toss USD 잔액이 늘어도 그 초과분은 JDSS가 다시 매수에 쓰지 못한다.

손실 후에는 실제 JDSS 가용 원금이 줄어들 수 있다. 이후 JDSS 이익으로 손실을 회복해 $50,000까지 돌아오는 것은 허용하지만, $50,000을 넘어선 이익은 다시 위험자금으로 쓰지 않는다.

## 2. 월간 쌍발 코어

코어는 큰 상승 추세를 오래 따라가는 저빈도 포지션이다. 각 기초자산을 독립적으로 판단한다.

1. 완료된 월말 종가만 사용한다.
2. 최근 6개월 월말 종가의 단순이동평균(SMA)을 계산한다.
3. 월말 종가가 6개월 평균보다 높으면 대응 레버리지 ETF 코어를 ON으로 본다.
4. OFF→ON 첫 달 목표는 **고정 원금 $50,000의 10% = 종목당 약 $5,000**이다.
5. 다음 월말에도 ON이면 **15% = 종목당 약 $7,500**을 목표로 한다.
6. ON이 유지되는 동안 15%를 유지한다.
7. OFF가 되면 목표를 0%로 낮춘다. 다음 ON은 다시 10%부터 시작한다.
8. 목표수량은 매수수수료를 포함해 정수주 내림한다.
9. 목표와 현재 코어 차이가 고정원금의 0.5%보다 작으면 불필요한 거래를 하지 않는다.
10. 코어 매수는 Telegram 2단계 승인이 필요하고, 위험축소 코어 매도는 자동이다.

코어의 사이징 기준은 계좌 평가액이나 누적 수익이 아니라 항상 **$50,000**이다.

## 3. JDSS H40-S3 부스터

부스터는 TQQQ/SOXL이 크게 눌린 뒤 반등 가능성이 커졌을 때 짧은 스윙을 노리는 부분이다.

- 종목별 H40 자금상한: **$20,000 = 고정원금의 40%**
- 3단계 S3 분할매수: 40% / 30% / 20%
- 누적투입: 40% → 70% → 90%
- 따라서 정상 한 사이클 최대 신규투입액: **$18,000 = 고정원금의 36%**
- 1차: 조건 충족 시 H40 cap의 40%, 약 $8,000
- 2차: 최초 체결가 대비 -2% 이하 + 점수 55 이상, 누적 약 $14,000
- 3차: 최초 체결가 대비 -5% 이하 + 점수 55 이상, 누적 약 $18,000
- 하루 최대 한 단계만 추가매수
- 모든 부스터 매수는 Telegram 2단계 승인 필요

### 진입 게이트

- 총점 **55점 이상**
- 반등점수 **5점 이상**
- 시장 Regime이 RED가 아닐 것
- 신호가격 대비 추격 상한 5%
- SOXL 1차·3차는 SOXX 또는 SMH가 EMA60 아래인 약한 반도체 국면에서 차단

## 4. 점수의 의미

점수는 과매도만 보는 숫자가 아니다. 다음 다섯 축을 합쳐 “많이 눌렸고, 반등의 흔적이 있으며, 시장 상황도 감당 가능한가”를 판단한다.

- **Market Regime**: SPY/QQQ 계열의 큰 시장 상태. GREEN/YELLOW/RED로 구분
- **Oversold**: CCI(5,10), RSI(5,14), Bollinger Band로 얼마나 과하게 눌렸는지 측정
- **Reversal**: 양봉, 전일 종가 회복, EMA5 회복, 당일 고가권 마감 등 반등 흔적
- **Volume**: 거래량이 평소보다 늘었는지 확인
- **ATR**: 최근 변동성이 전략에 적절한 범위인지 확인

점수 자체만으로 주문하지 않는다. 점수·반등 게이트·시장 상태·현재 포지션 단계·가격조건을 모두 통과해야 후보가 된다.

## 5. 익절과 종료

- TP1: 평균매수가 +4%에서 현재 부스터 수량의 약 30% 매도
- TP2: 평균매수가 +10%에서 남은 부스터 전량 매도
- ATR 적응형 TP: OFF
- 재매수: OFF
- 자동손절: OFF
- 기간경과 강제청산: OFF

자동손절을 두지 않는 대신 신규·추가매수 조건, 최대 자금상한, 분할매수, 시장 RED 차단, SOXL 섹터가드로 위험을 제한한다. 이 구조는 백테스트에서 채택된 계약이며 임의로 손절 규칙을 추가하지 않는다.

## 6. 같은 Toss 계좌에서의 자금 분리

JDSS는 브로커의 전체 USD 잔고를 전략자금으로 보지 않는다.

- `positions`: JDSS 부스터 수량·원가·TP 상태
- `core_positions`: JDSS 코어 수량·원가·추세 상태
- 주문원장: JDSS 주문의 체결수량·체결가격·수수료
- 개인 USD/QQQ/QQQM: JDSS 원장 밖의 자산

JDSS의 원금 사용액은 현재 코어·부스터 원가와 미체결 BUY 예약액을 포함해 계산한다. 신규 BUY는 다음 세 조건 중 가장 작은 한도 안에서만 허용한다.

1. 고정원금 $50,000에서 아직 쓰지 않은 원금
2. JDSS 주문원장에서 계산되는 실제 가용 현금
3. 실제 Toss USD 주문가능금액

따라서 개인 현금이 많이 들어와 있어도 JDSS가 가져다 쓸 수 없다. 반대로 JDSS 손실로 실제 전략현금이 부족하면 개인 현금으로 자동 보충하지 않는다.

브로커가 TQQQ/SOXL을 한 종목 수량으로 합쳐 보여주므로 개인 TQQQ/SOXL을 같은 계좌에 추가 보유하면 JDSS 원장과 분리할 수 없다. 이 경우 정합성 검사에서 SAFE_MODE가 될 수 있으므로 금지한다.

## 7. SGOV 제거 계약

V3.1.1에서는 `idle_cash.enabled=false`다.

- JDSS 유휴현금은 USD 그대로 유지
- SGOV 자동매수·자동매도 없음
- 전략 진입을 위해 SGOV를 먼저 팔아야 하는 과정 없음
- Telegram 명령 메뉴에서 SGOV 항목 제거
- Reconciliation도 SGOV 관리수량을 JDSS 필수상태로 취급하지 않음

이 결정의 목적은 소규모 유휴수익보다 **수수료·체결복잡성·운영단순성**을 우선하는 것이다.

## 8. 주문·승인·안전장치

- 데이터: 완료된 일봉/월봉만 사용
- 매수 허용 세션: pre-market, after-hours
- regular 세션 신규매수: OFF
- 매수 지정가 기본 버퍼: +0.5%, 단 단계별 가격상한과 추격상한을 넘지 않음
- 검토 승인 TTL: 480분
- 최종 실행 승인 TTL: 60초
- 코어·부스터 모든 BUY: Telegram 2단계 승인
- 위험축소 SELL 및 TP: 자동
- 주문 결과 `UNKNOWN`: 재주문을 추정하지 않고 SAFE_MODE
- 브로커 수량/DB 수량 불일치: SAFE_MODE
- 열린 주문의 broker id 누락 또는 정합성 불일치: SAFE_MODE
- dry-run 재시작 시 확인 가능한 원장만 복원하고 애매한 PARTIAL/UNKNOWN은 추정 복구하지 않음

## 10. 승격·배포 게이트

`main` 병합 전 다음을 모두 통과해야 한다.

1. Ruff
2. 전체 pytest
3. `jdss validate-config`
4. production V3 백테스트
5. dry-run 통합 테스트
6. Security workflow
7. 문서·설정·코드 계약 정합성

Oracle 배포는 항상 forced `dry_run`이며 live 잠금은 별도 승인 전 해제하지 않는다. `config_version` 변경 시 기존 열린 포지션·미체결 주문이 있으면 배포 스크립트의 안전검사가 전환을 막을 수 있으며, 이를 우회하지 않는다.
