# JDSS V3.1 백테스트 보고서

현재 개발 계약은 [`JDSS_FINAL_SPEC.md`](JDSS_FINAL_SPEC.md)의 **JDSS-3.1.0-TWIN-H40-S3**다. 정식 수치와 실행 규칙은 `strategy.yaml`, 재현 결과는 GitHub Actions 연구·백테스트 로그와 Artifact를 기준으로 한다.

## 가장 먼저: “실제 적용 로직으로도 같은 결과인가?”

**전략 계산 기준으로는 그렇다.** 연구에서 고른 V3.1 후보를 임시 연구코드로만 남겨두지 않고, main의 정식 production 백테스트 경로로 다시 실행했다. 핵심 성과는 연구 후보와 정확히 일치했다.

다만 다음 세 단계를 구분해야 한다.

| 단계 | 무엇을 검증하는가 | 현재 상태 |
|---|---|---|
| 연구 백테스트 | 어떤 전략 파라미터가 더 나은가 | 완료 |
| production 백테스트 | 채택한 전략이 정식 코드에서도 같은 성과를 내는가 | **핵심 수치 정확히 일치** |
| 운영 dry-run | 승인 지연·미체결·부분체결·API 장애·재시작까지 안전한가 | 정상 플로우 + fault-injection 자동검증 강화 |

즉 **V3.1의 신호·점수·코어·익절 계산은 production 코드로 재현됐다.** 그러나 실제 Broker 체결은 Telegram 승인시간, 호가, 네트워크 장애 등에 따라 백테스트와 달라질 수 있다. 이 차이는 수익률을 억지로 같게 만드는 대상이 아니라, 운영 사고가 나지 않도록 dry-run과 fault-injection으로 방어하는 대상이다.

## V3.1 채택 요약

V3.0 이후 연구는 한 번에 여러 조건을 무작위로 탐색하지 않고 추세기간, 코어 진입비중, 부스터 자금 상한, 시장필터, 익절, 잔량청산, 추가매수 단계를 순차적으로 비교했다. 최종적으로 다음 단순 구조를 채택했다.

- 월간 추세: 10개월 → **6개월**
- 코어: ON 즉시 15% → **첫 ON 10%, 지속 시 15%**
- 부스터 자금 상한: 5% / `$1,000` → **40% / `$8,000`**
- 실제 S3 한 사이클 최대 신규투입: 자금 상한의 90%인 **36% / `$7,200`**
- 분할매수: 4단계 → **3단계 40/30/20, 누적 40/70/90**
- 추가매수: 최초 체결가 -2% / -5%
- TP1: +4%에서 약 **30%**
- TP2: **+10%**
- TP1 이후 기간 기준 잔여청산: **OFF**
- 재매수: **OFF**

`H40`은 종목별 자금 상한을 뜻한다. 현재 S3는 3단계 누적 90%까지만 사용하고 재매수도 OFF이므로 일반 사이클에서 `$8,000` 전액을 투입하지 않는다.

## production 코드와 백테스트가 공유하는 것

부스터 백테스트는 production과 같은 핵심 계산 함수를 사용한다.

- 지표 계산
- 시장 Regime 계산
- JDSS Score 계산
- 1·2·3차 진입 판단
- -2% / -5% 추가매수 기준
- SOXL 섹터 가드
- TP1 / TP2 가격·수량 계약

포트폴리오 백테스트는 코어와 부스터가 `$20,000` 현금을 공유하고, 6개월 월간 코어와 SGOV를 함께 계산한다.

따라서 “연구용 코드에서는 좋았는데 실제 production 전략 계산은 다르다”는 문제는 현재 재검증에서 발견되지 않았다.

## production 백테스트가 실제 주문과 완전히 같지는 않은 부분

실제 bot에는 백테스트보다 더 많은 상태가 있다.

| 실제 운영 변수 | 백테스트 | 운영 코드 |
|---|---|---|
| Telegram 승인 지연 | 단순화 | 현재가·수량 재검증 |
| 지정가 미체결 | 모델 체결규칙 | PENDING 모니터 |
| 부분체결 | 단순화된 모델 | 누적체결 delta 원장 반영 |
| 주문 거절 | 성과모델에 직접 없음 | 재승인 또는 안전중단 |
| Broker 응답 UNKNOWN | 없음 | SAFE_MODE |
| Yahoo/Broker API 장애 | 없음 | 오류로그 + 재시도 + 작업 격리 |
| 서버 재시작 | 없음 | DB 원장 복원 + Reconciliation |
| SGOV 현금화 지연 | 일수익률 모델 | 실제 현금화 완료 후 최종승인 |

이 때문에 실제 운영 수익률이 백테스트와 숫자 하나까지 같을 것이라고 가정하면 안 된다. 운영 코드는 **실제 체결이 달라질 때 원장을 틀리게 만들거나 중복주문을 내지 않는 것**을 우선한다.

## 운영 fault-injection 검증

정상적인 E2E dry-run 외에 다음 예외 시나리오를 전용 `JDSS V3 Dry Run` 게이트에서 검증한다.

- 코어 매수 `REJECTED` → 동일 신호를 재승인 가능 상태로 복구
- 재승인할 때 이전 주문 ID를 재사용하지 않음
- 코어 매수 부분체결 후 취소 → 체결분 보존 + 잔여분 재승인
- 코어 위험축소 SELL 부분체결 후 종료 → SAFE_MODE
- 주문 결과 `UNKNOWN` → 성공으로 추정하지 않고 SAFE_MODE
- Broker 주문 유실 → SAFE_MODE
- TP1 이후 TP2 취소 → 자동 TP2 복구
- dry-run 재시작 → 보유수량·managed cash·주문 sequence 복원
- 동일 오류 Telegram 알림 rate-limit + SQLite 이벤트는 계속 기록
- production E2E 테스트가 최종 `FinalTradingService`를 직접 사용

이 테스트의 목적은 백테스트 수익률을 바꾸는 것이 아니라 **실제 적용 코드가 예상치 못한 사건에서도 전략 원장을 훼손하지 않는지** 확인하는 것이다.

## 탈락한 주요 후보

- 6M+10M 이중 확인, 6M+3M slope: 단순 6M보다 열위
- QQQ EMA60 / GREEN-only 부스터 필터: 수익 감소 대비 MDD 개선 없음
- Score≥92에서만 45/50% 확대: 실제 노출 변화 없음
- 부스터 자금 상한 45~50%: Sharpe 개선이 사실상 포화되고 MDD 증가
- TP2 +8%: +6%와 +10% 사이에서 우월하지 않음
- TP1 이후 20/40거래일 잔량청산: 제한 없음보다 열위
- Rebuy ON: 장기 전체에서 5회 체결에 불과해 표본이 작고 개선폭이 미미

## 해석 제한

- 과거 성과는 미래 성과를 보장하지 않는다.
- TQQQ·SOXL은 레버리지 ETF라 경로 의존성, 급락, 변동성 소모가 크다.
- 무손절 규칙은 장기 고착과 큰 미실현손실을 만들 수 있다.
- yfinance 조정 일봉과 모델링된 체결은 실제 호가·세금·환전·승인 지연을 완전히 재현하지 않는다.
- production 백테스트 동등성은 “전략 계산 코드가 같음”을 뜻하며, 실제 모든 주문 체결을 보장한다는 뜻이 아니다.
- V3.1.0도 이 한계 때문에 live가 아니라 dry-run 잠금을 유지한다.
