# JDSS 쉬운 전략·거래 가이드 — 현재 운용판

현재 설명 대상은 **JDSS V3.2.2**입니다. 빠른 이해가 필요하면 [ONE_PAGE_REPORT.md](ONE_PAGE_REPORT.md)를 먼저 읽습니다. 숫자와 예외조건의 최종 기준은 [`strategy.yaml`](../strategy.yaml)과 [`JDSS_FINAL_SPEC.md`](JDSS_FINAL_SPEC.md)입니다.

이 문서는 쉬운 전략 설명·거래 흐름·용어·승인된 기준 백테스트 결과의 소유 문서입니다. 다음 버전에서도 새 가이드를 만들지 않고 이 파일을 현재판으로 갱신하며, 과거판은 [`HISTORY.md`](HISTORY.md)와 Git tag에서 확인합니다.

## 1. 큰 그림: 세 개의 층

JDSS V3.2.2는 서로 다른 역할의 세 층을 합친 전략입니다.

1. **속도 조절기**: QQQ 시장 노출을 0.5 / 1.0 / 1.25 / 1.5배로 정합니다.
2. **반도체 선택기**: 레버리지 부분을 TQQQ에만 둘지, TQQQ·SOXL로 나눌지 정합니다.
3. **5% 타점 부스터**: 기존 H40-S3 과매도 신호가 활성화되면 QQQ 최대 5%를 3배 ETF로 바꿉니다.

이 세 층이 만든 **목표비중**과 **현재 실제 수량**의 차이만 매매합니다.

## 2. 0.5 / 1.0 / 1.25 / 1.5배 결정

새 달 첫 거래일 종가가 완전히 확정된 후 다음 순서로 판단합니다.

### 2.1 변동성 브레이크

QQQ의 20거래일 일간수익률 표준편차를 1년 기준으로 환산한 값이 30% 이상이면 다른 신호가 좋아도 **0.5배**입니다. 월중에 이 조건이 발생하면 즉시 감속하지만, 같은 달에 다시 가속하지는 않습니다.

### 2.2 장기 추세와 추세 투표

- QQQ 종가가 SMA200 이하이면 **1.0배**
- SMA50 > SMA200이고 63일·126일 수익률이 모두 양수이면 **1.5배**
- 아래 다섯 질문 중 3개 이상이 참이면 **1.25배**
- 나머지는 **1.0배**

다섯 질문은 21일 수익률 양수, 63일 수익률 양수, 126일 수익률 양수, SMA50 > SMA200, SMA200의 21일 기울기 양수입니다. 지표 계산 기간이 부족한 초기 구간은 1.0배를 사용합니다.

~~~mermaid
flowchart TD
    A["새 달 첫 거래일 종가 확정"] --> B{"20일 연환산 변동성 ≥ 30%?"}
    B -->|"예"| L05["0.5x"]
    B -->|"아니오"| C{"QQQ ≤ SMA200?"}
    C -->|"예"| L10["1.0x"]
    C -->|"아니오"| D{"SMA50>SMA200 그리고 63d·126d>0?"}
    D -->|"예"| L15["1.5x"]
    D -->|"아니오"| E{"5개 추세 표 중 3개 이상?"}
    E -->|"예"| L125["1.25x"]
    E -->|"아니오"| L10
~~~

## 3. 목표 노출을 실제 ETF로 바꾸기

3배 ETF 비중은 `(target leverage - 1) / 2`로 계산합니다. 예를 들어 QQQ 75% + TQQQ 25%는 `0.75×1 + 0.25×3 = 1.5`배입니다.

| 목표 노출 | QQQ | 3배 ETF 슬리브 | 현금 |
|---:|---:|---:|---:|
| 0.5x | 50% | 0% | 50% |
| 1.0x | 100% | 0% | 0% |
| 1.25x | 87.5% | 12.5% | 0% |
| 1.5x | 75% | 25% | 0% |

### RS6M ON/OFF

SOXX의 126거래일 수익률이 0보다 크고 QQQ의 같은 기간 수익률보다도 크면 RS6M ON입니다.

- OFF: 3배 ETF 슬리브를 TQQQ에 100% 배정
- ON: 슬리브를 TQQQ 50% + SOXL 50%로 배정
- 월중 ON 조건 상실: SOXL 부분을 TQQQ로 이동
- 일단 이탈: 다음 달 reset 전까지 SOXL 재진입 금지

정밀한 하루를 맞히려는 규칙이 아니라, 우위가 깨지면 먼저 후퇴하고 새 달에만 다시 판단하는 구조입니다.

## 4. H40-S3 5% virtual overlay

기존 시스템의 CCI, RSI, 볼린저밴드, 반등, 거래량, ATR 점수와 분할진입 사이클은 계속 계산합니다. 다만 별도 $20,000 전략으로 직접 주문하지 않습니다.

- TQQQ 가상 사이클만 ON: QQQ 5%를 TQQQ로 교체
- SOXL 가상 사이클만 ON: QQQ 5%를 SOXL로 교체
- 두 사이클 모두 ON: QQQ 5%를 TQQQ 2.5% + SOXL 2.5%로 교체

현물 5%를 1배에서 3배로 바꾸므로 유효 노출을 최대 약 0.10배 추가합니다. 가상 상태는 미래 데이터를 쓰지 않도록 한 거래일 지연해 반영합니다.

## 5. HWM75: 수익을 모두 다시 걸지 않는 복리

시작 위험원금은 $50,000입니다. 완결 거래일 종가 평가액으로 새 최고점을 만들면 초과이익의 75%만 위험예산에 넣습니다.

`HWM75 예산 = min(현재 평가액, 50,000 + 0.75 × max(0, 최고 평가액 - 50,000))`

| 상황 | 최고 평가액 | 현재 평가액 | 위험예산 |
|---|---:|---:|---:|
| 시작 | $50,000 | $50,000 | $50,000 |
| 새 최고점 | $60,000 | $60,000 | $57,500 |
| 이후 하락 | $60,000 | $52,000 | $52,000 |
| 더 큰 하락 | $60,000 | $45,000 | $45,000 |

나머지 25% 이익은 JDSS 현금이지만 위험예산 확대에는 쓰지 않습니다. 손실이 나도 개인 현금을 자동으로 넣어 원금을 복구하지 않습니다.

## 6. 신호에서 체결까지

~~~mermaid

    C --> D{"현재수량과 목표수량의 차이"}
    D -->|"위험축소"| E["SELL 자동 실행·체결 반영"]
    D -->|"위험증가"| F["BUY 신호 저장"]

    L --> M
    M -->|"정상"| A
~~~

### BUY 2단계 승인: 두 번 확인하는 이유

- 1차는 현재가, 상한가, 계획금액, 최대수량을 보는 검토 단계입니다.
- 2차는 짧은 유효시간 안에 실제 주문을 확정하는 단계입니다.
- 두 단계 사이에 가격·수량·시장 세션이 바뀌면 기존 승인을 버리고 다시 확인합니다.
- 위험을 줄이는 SELL은 승인을 기다리지 않습니다.

따라서 현재 계약에서 **BUY는 반자동, 위험축소 SELL은 자동**이 맞습니다. 시스템이 매수 필요량을 계산해도 사람의 두 번의 확인 없이는 실행하지 않습니다. SOXL→TQQQ 전환처럼 한쪽을 줄이고 다른 쪽을 늘리는 경우에도 SOXL 축소 SELL은 자동 처리 대상이고 TQQQ 증가 BUY는 별도 승인을 기다립니다.

### 동시성·재시작 보호

- 이미 대기 중인 코어 BUY와 아직 원장에 반영되지 않은 체결수량도 잔여 목표에서 먼저 뺍니다.
- 목표비중이 바뀌면 기존 코어 BUY·SELL을 취소·정산한 후 새 목표를 계산하며, 만료된 BUY도 감시기가 취소합니다.
- 완결봉에서는 목표비중만 기억하고, 실제 목표주수는 다음 거래일 주문 세션이 시작된 후 그때 가격으로 한 번 고정합니다.
- 목표주수 고정과 자동 위험축소 SELL도 허용된 주문 세션에서만 실행하며, 토스 주문 점검시간인 08:50~08:59 KST에는 주문하지 않습니다.
- 동시에 두 승인이 도착해도 SQLite `BEGIN IMMEDIATE` 안에서 목표수량과 HWM75 예산을 다시 검사합니다.
- 같은 `clientOrderId`가 재시도되면 다시 주문하지 않습니다. 브로커 최신 상태를 DB에 먼저 저장한 뒤 체결 차이만 원장에 반영합니다.
- 브로커가 돌려준 주문번호·종목·매매방향·수량이 예약한 주문과 다르면 체결로 믿지 않고 `UNKNOWN`으로 멈춥니다.
- 과거 H40-S3 직접 BUY 신호가 DB에 남아 있어도 V3.2.2 실행 계층이 무효화합니다.

## 7. forced dry-run과 실제 Toss 조회의 경계

현재 운영에서 ‘계좌’라는 말은 두 종류를 구분해야 합니다.

| 구분 | 현재 쓰임 | 주문과 정합성 |
|---|---|---|
| SQLite JDSS 원장 | 모의 보유수량·현금·주문·승인 상태를 영속 보관 | 모의 브로커와 대조하고 재시작 때 복원 |
| 모의 브로커 | 시세를 이용해 dry-run 주문과 체결을 흉내 냄 | 실제 Toss 주문을 만들지 않음 |
| Toss 조회 전용 경로 | `/account`, 계좌 요약, `toss-smoke`에서 실제 계좌를 읽음 | 모의원장에 자동 채택하지 않고 실주문도 하지 않음 |

따라서 forced dry-run에서 ‘reconciliation 성공’은 **현재 모의 주문 경로와 SQLite가 일치한다는 뜻**입니다. 실제 Toss 보유수량과 JDSS 모의원장이 같다는 뜻은 아닙니다. Toss 조회 실패도 모의 체결을 실제 체결로 바꾸지 않습니다.

## 8. 처음 전략을 계좌에 적용하기 전 preflight

실제 계좌 적용은 전략을 선택하는 것과 별도의 운영 변경입니다. 현재 live hard lock이 유지되므로 아래 항목은 자동으로 실거래를 켜는 명령이 아니라, 향후 변경 전에 모두 증명해야 할 **필수 게이트**입니다.

1. `CURRENT_WORK.md`, `strategy.yaml`, package와 공식 사양의 전략 ID·버전이 일치하는지 확인합니다.
2. 설정 검증, 테스트, no-lookahead 기준 백테스트와 배포 대상 SHA 검증을 통과합니다.
3. 기존 SQLite의 스키마·전략 세대·열린 주문·부분체결·UNKNOWN·legacy 상태를 검사하고 복구 가능한 백업과 명시적 migration plan을 준비합니다.
4. 실제 Toss의 QQQ/TQQQ/SOXL 보유수량, 열린 주문, 주문가능금액을 조회합니다. 개인 동일 티커가 섞였거나 출처를 증명하지 못하면 적용하지 않습니다.
5. dry-run에서 최초 목표 산출 → 자동 위험축소 → BUY 2단계 승인 → 부분체결/재시작 → reconciliation을 한 사이클 이상 확인합니다.
6. SAFE_MODE 사유가 없고, 주문 가격·수량·세션이 승인 사이에 바뀌면 재승인을 요구하는지 확인합니다.
7. 실제 주문 어댑터와 계좌 preflight가 해당 릴리즈에서 검증됐다는 증거와 대표의 별도 승인이 있을 때만 live 변경을 검토합니다.

현재 구현·배포에서 어느 단계까지 자동 점검되는지는 [`CURRENT_WORK.md`](../CURRENT_WORK.md)와 배포 검증 결과를 기준으로 판단합니다. 체크리스트 문구만 보고 구현됐다고 추정하거나 수동 확인을 생략하지 않습니다.

~~~mermaid
flowchart LR
    A["전략 선택"] --> B["설정·코드·백테스트 일치"]
    B --> C["기존 DB 백업·세대/주문 검사"]
    C --> D["실제 Toss 조회 preflight"]
    D --> E["forced dry-run 전체 사이클"]
    E --> F{"불일치·UNKNOWN·미완료가 0인가?"}
    F -->|"아니오"| G["SAFE_MODE 유지·원인 해결"]
    F -->|"예"| H["별도 live 검토·대표 승인"]
    H --> I["승인된 릴리즈에서만 운영 변경"]
~~~

## 9. SAFE_MODE와 계좌 규칙

다음 상황에서는 신규 BUY를 멈춥니다.

- 현재 주문 브로커의 수량과 SQLite JDSS 원장 수량 불일치
- DB와 브로커의 열린 주문 불일치
- 주문 결과를 확정할 수 없는 `UNKNOWN`
- 위험축소 SELL이 최종적으로 완료되지 않음
- V3.1.1 직접 H40 포지션·TP 상태가 남아 있음

V3.2.2가 직접 관리하는 티커는 **QQQ, TQQQ, SOXL**입니다. 같은 Toss 계좌에 개인 물량을 섞으면 브로커가 합산하므로 원장을 증명할 수 없습니다. QQQM처럼 다른 티커만 별도 수량으로 구분됩니다.

### 운영에서 생길 수 있는 대표 불일치

| 상황 | 잘못 처리하면 생기는 문제 | 안전한 처리 |
|---|---|---|
| 주문은 체결됐지만 프로세스가 응답 저장 전에 종료 | 재시작 뒤 같은 수량을 다시 매수 | broker receipt의 누적 체결에서 원장 적용분을 뺀 delta만 반영 |
| 누적 체결수량은 같지만 누적 체결금액이 갱신 | 원가·현금이 틀어짐 | 수량뿐 아니라 누적 notional도 이전 적용값과의 delta로 반영 |
| `PENDING_CANCEL`·`PENDING_REPLACE` 같은 중간 주문상태 | 열린 주문을 종료 주문으로 오인 | 모든 비종료 상태를 열린 주문으로 예약·감시 |
| 종료 주문이 늦은 응답으로 다시 `PENDING`이 됨 | 같은 주문을 다시 감시하거나 중복 처리 | 누적 체결수량 감소와 종료 상태의 재개를 DB에서 거부 |
| 같은 전략 generation의 저장 목표는 남았지만 BUY 신호가 사라짐 | 재시작 뒤 목표 미달을 영구 방치 | 저장된 `target_qty`와 현재 보유·열린 주문의 차이만 복구 후보로 계산 |
| 자동 SELL이 부분체결·UNKNOWN·취소확인 실패 | 줄이지 못한 위험 위에 새 BUY 추가 | SELL 종료·원장 반영·정합성 확인 전 BUY 차단, 필요하면 SAFE_MODE |
| 실제 Toss 계좌와 dry-run 모의원장을 같은 것으로 해석 | 개인물량 채택 또는 잘못된 실거래 준비 판정 | 두 출처를 분리 표시하고 실제 계좌는 별도 read-only preflight |

## 10. QQQ 대비 백테스트

공통 조건은 2011-01-01~최신 완결 거래일, 초기 $50,000, 매수·매도 수수료 각 0.1%, 슬리피지 0.1%, next-session execution, HWM75, SGOV OFF입니다. 보고 시작일은 빈 계좌의 최초진입일로 보며, 1~3번째 미국 거래세션 50%, 4~6번째 75%, 7번째부터 100%의 목표 한도를 적용합니다. 백테스트에서는 각 단계 체결을 가정해 최소 세션 경과 후 자동 진행하고, production은 `/onboarding` 운영자 승인을 계속 요구합니다.
